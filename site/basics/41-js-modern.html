ES6+ 总览：你其实一直在用新写法

JavaScript 的版本现在按年份发布：2015 年那一版改得最狠（俗称 ES6，正式名叫 ES2015），之后每年小步快跑。 本教程从第二十七式起，用的就已经是现代写法了——这一节把它们排成队列， 逐个对号入座：

例 1 · 新语法尝鲜盘：一次把常用的都过一遍

    模块：把代码分成几家人

    文件多了就要分家：一个文件只做一件事，别的文件按需引用它。 现代 JavaScript 的官方答案是 ES 模块：

    本站为什么不用 ES 模块

    <script type="module"> 在 file:// 下会被浏览器的 安全策略拦下（模块强制走 CORS，而本地文件“没有源”）—— 双击打开就白屏。本站的铁律是“双击即开、零构建”，于是全部改用 经典脚本按顺序引入：谁先谁后写清楚，需要共享的东西挂在 window 的一个命名空间上。本站的 DOJO 就是这么来的。 你的项目若一开始就配本地服务器或打包工具，用模块当然更清爽—— 先看运行环境，再选工具。

    例 2 · 没有模块的年代怎么分家：挂一个命名空间

      兼容性：先检测，再决定

      你写的页面会被各种浏览器打开：有人用刚更新的，有人用三年前的手机。 面对新 API，成熟的套路不是“赌它一定在”，而是三步： 特性检测 → 能用就用 → 不能用就降级。

      名词 解决什么 代价
      特性检测“这台浏览器有没有这个能力”要写两套分支，但最稳
      降级没有新能力时给一个朴素但可用的方案体验打折，功能不丢
      polyfill给缺失的 API 补一个实现多下载一段代码；补不了的 API（如语法）没办法
      转译（Babel 等）把新语法翻译成老语法需要构建步骤，代码不再是手写的那份
      例 3 · 现场体检：你这台浏览器支持哪些？

        顺带提一个同样适合“先检测再说”的能力：Element.prototype.animate() ——Web Animations API。它是浏览器内置的动画接口， 用一行 JS 就能跑关键帧，不必引任何库，也不必先写 @keyframes； 第二十四式学的动画概念（时长、缓动、循环）在这套接口里一一对应：

        什么时候用它？动画参数要由 JS 算出来的时候 （比如“跟随点击位置”“按数据大小决定幅度”）——CSS 写不出运行时才知道的数， animate() 可以；反过来，纯装饰性的动画还是写在 CSS 里更省心 （第二十四式的分工）。

        继续往哪走：一张小地图

        基础篇到这里，HTML、CSS、JavaScript 三样基本功都过了一遍。 往下的路大致分成三条，挑你眼下用得上的那条走：

        方向 值得先学 大致用在哪
        把页面做得更稳无障碍、性能、响应式细节任何要给别人用的页面
        把交互做得更顺Web API：IntersectionObserver、Clipboard、FileReader、Canvas图片懒加载、复制按钮、上传预览、画图
        把项目做大模块与打包、TypeScript、框架（Vue / React）多人协作、长期维护的应用

        查文档的手艺比背 API 重要：遇到不认识的属性，先翻 MDN 的 JavaScript 参考， 看清“语法、返回值、浏览器支持”三栏；本站藏经阁里的两页速查 （工具类、jQuery 方法）也随时可以翻。

        心法

        语言每年都在长，但基本功长得慢：结构清晰、命名老实、错误处理到位、 界面对键盘和读屏友好——这些十年后依然吃香。新语法是工具，不是功课。

        这些没讲，是有意的：一份“深水区”清单

        基础篇刻意没有展开这几样： 迭代协议（for...of 背后的 [Symbol.iterator]）、 生成器 function*、Proxy / Reflect、 WeakMap / WeakSet 的深入用法（第三十三式只说清了“弱引用”这层意思）、 Web Worker、自定义元素与 Shadow DOM。 它们属于“框架作者和库作者的工具箱”，新手做静态页面时几乎用不到； 现在硬啃，容易把力气花在一年也碰不上一次的地方。 等到你真的要写一个库、或者被某个报错指到这里，再回来查就行—— 本站按“能当字典查”来写，缺的那几页用 MDN 补，正好。

        本式小结

        • ES6+ 的主力：块级作用域、箭头函数、模板字符串、解构与展开、默认与剩余参数、 类、Promise / async-await、?. 与 ??、类字段；
        • 模块用 import/export，但 type="module" 在 file:// 下会被拦；本站改成经典脚本按顺序引入 + DOJO 命名空间；
        • 兼容性三步：特性检测 → 能用就用 → 不能用就降级； polyfill 补 API，转译补语法；
        • 检测新语法可以用 new Function("…") 把代码包成字符串， 免得老浏览器一上来就解析报错；
        • 查文档先看三栏：语法、返回值、浏览器支持；
        • 基础打完，往下按“更稳 / 更顺 / 更大”三条路选一条继续走。
        练功 · 第四十一式
        1. 下面这段老代码，用本式学过的写法重写一遍（要求：箭头函数 + 解构 + 模板字符串）： var user = { name: "阿朱", city: "临安" }; function greet(u) { return "你好，" + u.name + "，来自 " + u.city; }
        2. 给你自己的页面加两处“特性检测 + 降级”：例如 IntersectionObserver 不存在时就一次性加载全部内容、 localStorage 不可用时就只在内存里记状态。
        3. 思考：本站选择“不用 ES 模块、按顺序引入经典脚本”，换来了什么、 又失去了什么？如果你要给三五个人的项目选方案，会怎么权衡？
        参考答案 1

        注意参数位置的解构 ({ name, city })——调用时照旧传整个对象， 函数体里就不用再写 u.name 了。两行输出完全一样， 说明新写法只是“写起来顺”，不是换了一套逻辑。

        参考答案 2

        两个细节：localStorage 的检测要放在 try/catch 里 （隐私模式下可能直接抛错），检测完立刻把探针键删掉； 降级方案要保证“功能不丢”，只是体验朴素一点—— 这就是渐进增强的思路。

        参考答案 3

        换来的：双击即开、零构建、零依赖—— 任何一台电脑、任何一个静态服务器都能直接跑，调试时不用等打包， 三年后回头看，代码还是那份代码。失去的：没有静态分析、 没有依赖管理、没有按需加载，全靠人工约束“谁先加载谁后加载”， 代码一多就容易乱（这也是本站用 DOJO 命名空间 + 单一数据源来收拢的原因）。 三五个人的项目我会这样权衡：如果交付物是“一个可双击打开的教程站/小工具”， 经典脚本更划算；如果要长期迭代、多人协作、还要接接口， 就该上构建与模块——工具跟着场景走，别跟着潮流走。
