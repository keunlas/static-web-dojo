写代码就是不断和各种错误打交道。这一式教你两件事： 怎么接住错误（别让它把整个页面拖垮）， 怎么找到错误（控制台、断点、调用栈）。 学会之后，报错就从“灾难”变成了“提示”。

本式要点
  • 认得错误对象三件套（name / message / stack）与常见错误类型
  • 会用 try / catch / finally，并知道它们的执行顺序与“别吞掉错误”
  • 会 throw，会写自定义错误类，并用 instanceof 区分处理
  • 知道为什么异步回调里的错误抓不到（第三十九式细讲）
  • 掌握控制台家族与断点调试的基本套路

接住错误：try / catch / finally

要点 说明
只包“可能出错的一小段”把整个函数的代码都塞进 try 里，会让你看不出到底哪一步出的错
finally 一定执行哪怕 try 里 return 了、或者 catch 里又抛了，finally 都会走完
catch 的参数可以省略catch { … }（ES2019）——当你不关心错误对象时更清爽
不要吞掉错误空的 catch {} 会让错误悄无声息地消失，比崩溃更难查； 接不住就 throw err; 继续往上抛
能恢复才接“读取配置失败就用默认值”属于可恢复；“数据格式全错”就该让它暴露出来

      异步的错误，try/catch 抓不到

      try 只能接住“在它执行期间抛出的错误”。 定时器与事件回调里的错误发生在很久以后，那时 try 早就执行完了：

      这背后的原因是“事件循环”：回调会被排到队列里，等当前这段代码跑完再执行。 第三十九式会把这件事讲透，现在先记住结论： 异步代码要各自处理自己的错误。 真要兜底，可以监听全局的 window.onerror 与 window.onunhandledrejection， 但那属于“最后一道网”，不该拿来代替正常的错误处理。

        常见错误速查（新手高频）

        报错 / 现象 多半是这件事 怎么改
        Cannot read properties of null 元素还没解析出来就去操作它，或选择器写错了 脚本放 </body> 前 / 加 defer；检查 id 拼写
        xxx is not defined 名字拼错、忘了声明，或引用的脚本没加载 看 name 与拼写；确认依赖顺序
        xxx is not a function 方法名拼错、对象类型不对（比如把字符串当数组用） 用 typeof / Array.isArray 打印一下真身
        函数返回 undefined 忘了写 return，或者 return 后面换行了 检查分支是否都有返回；别在 return 后换行
        循环里的函数都返回同一个值 var 的函数作用域 + 闭包（第三十一式） 把循环变量换成 let，或用 forEach
        回调里 this 不是想要的对象 this 由调用方式决定（第三十三、三十五式） bind(this)，或用箭头函数包一层
        0.1 + 0.2 !== 0.3 引起的判断失败 浮点精度（第三十四式） 比差值，或改用整数运算
        拿到的数据是 undefined 键名写错、异步还没回来、接口字段改了 先 console.log 整个对象看看结构；用可选链兜底
        读调用栈的三步
        1. 看第一行：错误类型与说明；
        2. 看第一条带文件名与行号的记录：那里通常就是出错位置，点一下直接跳过去；
        3. 往下看调用链：谁调用了谁——顺着读，能还原出“事情是怎么走到这一步的”。

        本式小结

        • 错误对象的三件套：name（类型）、message（说明）、stack（调用栈）；
        • 常见类型：SyntaxError 语法错、ReferenceError 名字不存在、 TypeError 用法不对、RangeError 超范围；
        • try 包住可能出错的一小段，catch 处理，finally 收尾且一定会执行；
        • 别吞错误：空 catch 比崩溃更难查；处理不了就 throw 继续往上；
        • 自定义错误：class X extends Error，设好 name，配合 instanceof 分类处理；
        • 异步错误抓不到：定时器与 Promise 的失败要在各自的回调 / .catch / await 的 try 里处理（第三十九式细讲）；
        • 调试套路：console 家族打印状态、console.table 看表格、 debugger 与 Sources 断点单步、顺着调用栈找源头。
        练功 · 第三十六式
        1. 故意写三段会报错的代码（引用不存在的变量、对 null 取属性、 把数字当函数调用），用 try…catch 分别打印出 name 与 message。
        2. 写一个 parseScore(input)：输入不是数字或超出 0–100 时， 抛出自定义的 ScoreError（带 field 信息）； 调用处用 instanceof 区分“格式错误”与“其他意外错误”。
        3. 思考：为什么 try { setTimeout(() => { throw new Error("x") }) } catch {} 抓不到那个错误？请用“事件循环”说明，并写出两种正确的处理方式。

        参考答案 2

        要点：能预期的问题用自定义错误并提示用户；不能预期的错误继续往上抛， 让它出现在控制台里——那才是你应该去修的 bug。

        参考答案 3

        因为 setTimeout 只是登记了一个任务，然后立刻返回； try 里那一瞬间并没有任何错误发生，所以它执行完就结束了。 过一会儿（下一轮事件循环）浏览器才去执行那个回调， 此时 try 早已不在现场——错误当然抓不到。 两种正确做法： ①在回调内部自己处理： setTimeout(() => { try { … } catch (err) { … } }, 0)； ②如果是 Promise，就用 .catch() 或 async/await + try 来接： doWork().catch(err => …)。 想要全局兜底，还可以监听 window.onerror 与 window.onunhandledrejection，但那是最后一道网。
