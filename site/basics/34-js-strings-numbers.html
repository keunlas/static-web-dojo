这一式把四样“日常工具”打包讲完：字符串（处理文字）、 正则（按模式找文字）、数字（算账与格式化）、 日期（时间轴上的位置）。它们没有惊天动地的原理，但谁熟谁省事。

本式要点
  • 掌握字符串的查找、截取、替换、拆分、修剪、补齐与重复方法
  • 看懂正则的常用元字符与标志，会用 test、match、replace 解决常见问题
  • 知道浮点数的精度陷阱，会用 Math、toFixed、toLocaleString 处理数字
  • 会创建、读取、格式化日期，并避开时区与“月份从 0 开始”的坑

    正则的两条纪律
    • 不要用正则解析 HTML：嵌套结构它处理不了，要用 DOMParser 或 让数据以 JSON 形式传来（第三十七式会讲解析 HTML 的正确方式）；

    数字：精度、转换与 Math

    先说那个著名的问题：0.1 + 0.2 不等于 0.3。 原因是计算机用二进制存小数，而 0.1 与 0.2 在二进制里都是无限循环小数， 存进来就已经带了舍入误差。

      日期的三个常见坑
      • 月份从 0 开始：getMonth() 拿到 8 表示九月，显示时记得 +1；
      • 字符串解析有歧义："2026-09-14"（ISO）按 UTC 解析， "2026/09/14" 按本地时间解析。要精确控制，用 new Date(2026, 8, 14) 或带偏移的 "2026-09-14T00:00:00+08:00"；
      • Date 是可变的：setFullYear() 这类方法会改自己， 不像字符串那样返回新对象。要“另一个日期”就 new Date(原.getTime())。

      本式小结

      • 字符串不可变，方法都返回新串；速查里最常用的：trim、includes、 slice、replaceAll、split、padStart、repeat；
      • replace 只换第一个，全换用 replaceAll 或 /g； length 数的是编码单元，emoji 要用 [...str]；
      • 正则：test 判断有没有、match/matchAll 取结果、 replace 做替换（可用 $1 与函数）；具名组让代码更好读； 别用正则解析 HTML；
      • 数字：0.1 + 0.2 !== 0.3 是精度问题，比小数用 Number.EPSILON；金额建议用“分”做整数运算；
      • Number() 要整串合法、parseInt/parseFloat 能解析多少算多少； Math.floor/ceil/round/trunc/min/max/random 是日常工具；
      • 格式化交给 toLocaleString 与 Intl.NumberFormat，别手拼千分位；
      • 日期：月份从 0 开始、ISO 字符串按 UTC 解析、Date 自身可变； 计算用毫秒差，显示用 Intl.DateTimeFormat。

      3. 思考：为什么“比较两个浮点数是否相等”不能直接用 ===？请用 0.1 + 0.2 说明，并说出两种可行的替代做法。
      参考答案 1

      两种做法都值得会：拆开再拼适合还要对数字做运算的场合 （比如 Number(m) + 1）；正则替换适合格式规整、只做重排的场合。 注意 split("-") 得到的是字符串数组，要计算就得先 Number()。

      参考答案 2

      要点：内部一律用整数“分”做加减，只在最后显示时除以 100 并用 toFixed(2) 补两位小数——这样能绕开浮点误差累计的问题 （1999 + 2999 这种整数加法永远是精确的）。

      参考答案 3

      因为 0.1 与 0.2 在二进制里都是无限循环小数， 存进 64 位浮点数时已经被舍入过；两个舍入过的值相加， 结果自然与“十进制里算完再舍入”的 0.3 不完全相等—— 实测是 0.30000000000000004。 两种替代做法： ①比差值：Math.abs(a - b) < Number.EPSILON； ②换成整数运算（比如金额用“分”、长度用“毫米”）， 算完再换算回小数显示。第三种工程做法是引入专门的十进制库，但那是后话。
