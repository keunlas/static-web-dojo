前面三十六式，程序算完了、判断完了，页面上却什么都没变——因为还差最后一步： 把结果写回页面。这一式讲 DOM：JavaScript 伸进页面的那只手。

本式要点
  • 会用 querySelector 家族查找元素，知道 NodeList 与数组的差别
  • 分得清 textContent 与 innerHTML，并知道后者的安全风险
  • 会读写属性、data-*、类名与样式
  • 会创建、插入、删除、替换元素，并知道批量插入要用 DocumentFragment
  • 会读表单控件的“当前状态”（value / checked）

DOM 是什么

浏览器解析 HTML 之后，会在内存里建一棵节点树：每个标签是一个元素节点， 文字是文本节点，属性、注释也都是节点。这棵树就叫 DOM（Document Object Model，文档对象模型）。 JavaScript 通过 document 这个入口去访问它。

所以“改页面”就是这么回事：找到节点 → 改它的内容、属性、类名或位置。 下面四件事按顺序过一遍：查、读改、造型、增删。

第一件事：找到元素

方法 按什么找 返回
document.getElementById("x")id（全页唯一）一个元素或 null——最快
document.querySelector(选择器)任意 CSS 选择器第一个匹配的元素或 null
document.querySelectorAll(选择器)任意 CSS 选择器NodeList（静态快照，不会随后续改动更新）
getElementsByClassName / getElementsByTagName类名 / 标签名HTMLCollection（“活的”，DOM 一变它就变）
el.closest(选择器)从自己往上找祖先最近的那个祖先（含自己）或 null
el.matches(选择器)问“我符合这个选择器吗”true / false

两个实用的补充：querySelectorAll 返回的不是真数组， 想用 map/filter 就先转： [...list] 或 Array.from(list)； 在某个元素内部查找时，把 document 换成那个元素即可 （box.querySelector("li")）。

              给动态内容的三个习惯
              • 文本用 textContent；需要结构就 createElement 逐个拼（或用 <template> 克隆）；
              • 属性用 setAttribute 或直接赋值， 别把用户输入拼进 HTML 字符串里；href 这类要额外小心 （javascript: 开头的地址点击即执行）；
              • 要插的元素很多时，先攒进 DocumentFragment 再一次性插入；也尽量别在循环里边写边读——offsetHeight 这类读操作会逼浏览器立刻结算布局，例 4 的两种计时就是这件事的直观证据。

              表单控件的值

              表单是 DOM 操作的高频场景，记住每个控件“值放在哪”：

              控件 读值 说明
              文本框 / 密码框 / 多行文本input.value / textarea.value总是取当前输入
              复选框input.checked布尔值；value 是它提交时的值
              单选框组document.querySelector('input[name="x"]:checked')或配合 form.elements 遍历
              下拉框select.value（多选时 selectedOptions）取的是被选中项的值
              整个表单form.elements按 name 取用，如 form.elements.email.value

              还有一个好用的组合：new FormData(form) 能把整张表单的键值一次抓出来， 配合 Object.fromEntries(formData) 直接变成对象 （第四十式讲数据时还会遇到它）。

              本式小结

              • DOM 是内存里的节点树，document 是入口；改页面＝找到节点再改它；
              • 查找：getElementById 最快、querySelector(All) 最通用、 getElementsByClassName 是“活的”；NodeList 要用 [...] 转成数组；
              • 文本用 textContent、信任的 HTML 片段才用 innerHTML； 表单控件用 property（value / checked）而不是 attribute；
              • classList 切类名、style.setProperty 改变量、 getComputedStyle 读最终样式；
              • 增删改：createElement、append/prepend/before/after、 replaceWith、remove、cloneNode(true)； 批量插入用 DocumentFragment；
              • 安全：用户输入永远当文字处理，绝不拼进 HTML 字符串。
              练功 · 第三十七式
              1. 做一个“留言板”：一个输入框 + 一个按钮，点击后把输入内容作为新条目加到列表里 （要求：用 textContent，空输入不添加，新条目插在最前面）。
              2. 给每个留言条目加一个“删除”按钮：点击后把这一条从列表里移除 （提示：在回调里用 event.target.closest("li") 找到所属条目， 事件委托第三十八式会正式讲）。
              3. 思考：为什么 innerHTML 能够执行内容里的标签与脚本， 而 textContent 不能？这两种“信任级别”分别适合什么场景？
              参考答案 1

              四个细节都值得保留：trim() 挡掉纯空格、textContent 保证安全、prepend 让最新的在最上面、发完清空并聚焦输入框。

              参考答案 2

              两个关键点：①先判断 event.target 是不是删除按钮， 避免点条目本体也触发删除；②用 closest("li") 从按钮往上找所属条目——把事件绑在父容器上（事件委托）， 后来新增的条目就不用再单独绑定了。

              参考答案 3

              因为 innerHTML 的语义就是“把这段字符串当 HTML 解析”： 浏览器会按解析 HTML 的规则建出元素、设置属性， 而某些属性（如内联事件处理器、javascript: 地址）本就带有执行能力， 所以它能“执行内容里的脚本”。textContent 的语义是“这段字符串就是文字”， 标签只会原样显示，绝不会变成元素。 两种信任级别的使用场景很明确： 自己写死的、可信的 HTML 片段（比如从本地模板文件里取来的骨架） 可以用 innerHTML 省事； 任何来自用户、地址栏、接口的数据都必须走 textContent 或 createElement + textContent。 一句话：信任级别决定写法，而不是顺手决定写法。
