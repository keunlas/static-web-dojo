HTML 立了骨架，CSS 裁了外衣，接下来轮到“灵魂”了。 JavaScript 让页面从一张画变成一件工具：按钮点得动、表单算得出、数据记得住。 这一式先不急着写复杂逻辑，只把“脚本怎么进页面、怎么跑、怎么看结果”说清楚。

本式要点
  • 知道 JavaScript 负责什么，和 HTML / CSS 各管哪一段
  • 会用三种引入方式，特别是外部脚本；知道脚本该放在哪里、defer 有什么用
  • 会打开控制台看输出与报错，知道 console.log 是最常用的“探照灯”
  • 认得语句、注释、分号与严格模式，并能读懂三类常见错误

JavaScript 负责什么

三件套的分工，一句话就能记住： HTML 是骨架（有什么）、CSS 是外衣（长什么样）、JavaScript 是灵魂（会做什么）。 具体到页面上，JavaScript 常干这些事：

  • 响应操作：点击、输入、滚动时做点什么；
  • 改动页面：改文字、加类名、插入或删除元素（第三十七式）；
  • 计算与校验：算总价、算字数、检查表单填得对不对；
  • 存取数据：把读者的选择记在浏览器里，下次打开还在（第四十式）；
  • 与服务器交谈：拿数据、提交数据（第四十式会讲，且受 file:// 限制）。

它是编程语言，和 HTML / CSS 有本质区别： HTML 是“描述”，CSS 是“声明”，而 JavaScript 是一步步下命令—— 会判断、会循环、会记住东西。这也是为什么它是三样里最难、也最值得的那一样。

脚本怎么进页面

三种写法，第三种要避开：

写法 样子 什么时候用
外部脚本（推荐） <script src="app.js" defer></script> 正式项目：一份文件管多页，浏览器能缓存
内部脚本 <script>…</script> 直接写在页面里 只属于这一页的小逻辑、教程演示
元素事件属性 <button onclick="doSomething()"> 老写法，把结构与行为混在一起，新代码不要用

位置与时机是新手最容易撞墙的地方。回忆第十式那张表，这里换个角度再说一遍：

  • 放在 </body> 之前：页面内容都解析完了，脚本想找谁就找谁，最直观；
  • 放在 head 里但加 defer：边下载边解析，等页面就绪后按顺序执行—— 想在 head 里写脚本时用它；
  • 不加 defer 就放在 head 里：脚本会立刻执行，那时候 body 还没解析出来，你去取元素只会拿到 null——这是新手第一个“灵异事件”。

控制台：你的第二双眼睛

打开方式（三种任选）：

  1. 按 F12，或 Ctrl + Shift + I；
  2. 在页面上右键 →“检查”，再切到 Console（控制台）标签；
  3. 菜单里找“更多工具 → 开发者工具”。

控制台能干三件事，每一件都很重要：

  • 看输出：console.log() 打出来的内容都在这里；
  • 看报错：脚本出错时会显示错误类型、说明与行号，点行号还能跳到出错那一行；
  • 当场试代码：在控制台里直接输入 1 + 1 回车，会立刻回你 2—— 想验证一个小想法时，不必改文件、不必刷新。
心法：报错不是失败，是坐标

“Uncaught ReferenceError: x is not defined” 这样的红字，新手看着像判决书， 其实是浏览器在告诉你迷路的位置：类型、原因、哪一行。 读它三秒钟，比盲改代码三十分钟有用。

错误类型 常见原因 例子
ReferenceError 用了一个不存在的名字（拼错、忘了声明） Uncaught ReferenceError: tital is not defined
TypeError 把没有的东西当有来用（最常见：对 null 取属性/调用方法） Uncaught TypeError: Cannot read properties of null (reading 'textContent')
SyntaxError 语法本身写错了（少括号、少引号、中文标点） Uncaught SyntaxError: missing ) after argument list

    本式小结

    • HTML 结构、CSS 样式、JavaScript 行为；JS 是编程语言，逐步下命令；
    • 引入方式首选外部脚本 <script src="…" defer>；避免 onclick="…" 这类老写法；
    • 脚本放 </body> 之前，或放 head 里加 defer； 否则执行时元素还没解析出来，只能拿到 null；
    • 控制台三件事：看输出、看报错、当场试代码；console.log 是最常用的探照灯；
    • 注释是 // 与 /* */；语句结尾建议写分号，避开自动补分号的坑；
    • 脚本开头写 "use strict"; 让错误暴露得更早（模块与类内部自动严格）；
    • 报错格式是“类型 + 说明 + 位置”：认得 ReferenceError、 TypeError、SyntaxError 这三类，就已经能解决大半问题。
    练功 · 第二十七式
    1. 新建一个 app.js，用 defer 引进页面， 在里面用 console.log 打印一句问候，再把它写进页面上某个元素里。
    2. 打开控制台，故意写错一个变量名（把 title 写成 tital）， 读一读报错信息：类型是什么？它说找不到什么？行号指向哪里？
    3. 思考：为什么“把脚本放在 </body> 之前”和 “放在 head 里加 defer”都能解决问题？它们解决的是同一件事吗？
    参考答案 1

    检查点：打开控制台能看到“脚本已经开始工作”；页面上那段占位文字被换掉了； 把 defer 去掉再试一次，多半会看到 Cannot read properties of null——那正是这一式讲的位置问题。

    参考答案 2

    报错大致长这样：Uncaught ReferenceError: tital is not defined。 拆开读：类型是 ReferenceError（引用错误）， 说明是“tital 没被定义”，行号指向那一行。 信息里已经写清了“我找不到叫 tital 的东西”——所以排查动作很明确： 检查拼写，或者确认那个变量是否真的声明过。

    参考答案 3

    它们解决的是同一件事的两个做法：让脚本在页面结构就绪之后再执行。 放到 </body> 之前，是因为浏览器从上往下解析， 走到这里时上面的元素已经全部存在了； 加 defer，则是浏览器帮你把这个“等一等”的活儿接了过去—— 脚本照常提前下载，但等页面解析完再按顺序执行。 实战建议：能用 defer 就用它， 脚本写在 head 里、结构更整齐，也不会因为后来有人挪动代码而失效。
