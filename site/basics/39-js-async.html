江湖上的活计，多半不能立等可取：水要烧开、信要送到、数据要等回话。 前面三十八式里，代码都是一口气跑完的；这一式学会等—— 等的时候不耽误别的事。

本式要点
  • 会用 setTimeout / setInterval 安排将来要做的事，并会取消
  • 理解 Promise 的三种状态，会用 .then / .catch / .finally
  • 会用 Promise.all / allSettled / race / any 组合多个异步任务
  • 会写 async 函数、用 await 拿结果、用 try/catch 接错误
  • 说得清事件循环里“同步 → 微任务 → 宏任务”的先后顺序

同步与异步：什么都不等的写法会出事

到目前为止，我们写的代码都是同步的：一行跑完才跑下一行， 顺序明明白白。可有些事天生快不了——下载一张图、问服务器要数据、等用户思考， 如果让浏览器“站在原地等”，整张页面就冻住了。

于是浏览器给了一个办法：把慢活儿交出去，登记一个回调， 自己继续往下跑；等慢活儿有结果了，浏览器再回头叫你。 这就是异步。最常见的异步入口有两个： 定时器（到点叫我）和 Promise（干完叫我）。

心法

异步不是“同时干两件事”的魔法，而是“先记下这事，别堵住后面”。 页面之所以能一边等数据一边还能滚动、还能点按钮，全靠这个“先记下”。

定时器：到点叫我

写法 意思 取消
setTimeout(fn, 毫秒)过一会儿执行一次 fnclearTimeout(编号)
setInterval(fn, 毫秒)每隔这么久执行一次，直到取消clearInterval(编号)
requestAnimationFrame(fn)下一次画面刷新前执行（做动画用它）cancelAnimationFrame(编号)

两个必须记住的事实：一是毫秒数只是“至少等这么久”， 主线程一忙，回调就会晚点；二是定时器不保证顺序， 连续几个 setTimeout(fn, 0) 也是排队来，不一定是“立刻”。

    Promise：一张“将来会有结果”的收据

    setTimeout 只解决“到点叫我”，可复杂点的活儿会有 成功和失败两种结局。Promise （承诺）就是为这件事设计的对象：它一诞生就是等待中（pending）， 将来要么兑现（fulfilled）、要么拒绝（rejected）， 而且只定一次，不会再改。

    自己造 Promise 的场合其实不多，日常更多是用别人返回的 Promise （比如第四十式要讲的 fetch）。真正的重点是： 拿到 Promise 之后怎么等它、怎么组合多个 Promise。

    组合方法 什么时候给你结果 适合
    Promise.all([...])全部成功才成功；任何一个失败就立刻失败几件事都要办成，缺一不可
    Promise.allSettled([...])全部有结局（成功或失败）才给你要逐条汇报，不怕个别失败
    Promise.race([...])第一个有结局的就给你（不论成败）超时控制：跟一个“到点就失败”的计时器赛跑
    Promise.any([...])第一个成功的给你；全失败才失败多个镜像源，谁先成谁算

      async / await：把异步写得像同步

      Promise 的 .then() 链越接越长就越难读。于是有了 async / await 这对语法糖： 在 async 函数里，await 一个 Promise 就等于“等它的结果”， 写起来和同步代码一样顺；出错则用 try/catch 接住， 跟第三十六式学过的错误处理完全一致。

      例 4 · async/await 走一遍：成功、失败、finally、allSettled

        最后一个常被忘掉的角落：异步的活儿也能取消。 定时器有 clearTimeout，而“正在路上的网络请求”要用一个专门的开关—— AbortController：它身上的 signal 递给 fetch， 想反悔时喊一声 abort()，请求就会被中止、await 那边抛出一个 AbortError：

        为什么要它？回到第三十八式的防抖搜索：用户每停一次手就发一次请求， 如果前一次还没回来，后面的结果可能晚到并把新结果覆盖掉。 正确姿势是：发新请求前先 abort() 掉上一个—— 这也是“Esc 停下正在加载的页面”“切走标签页就别再请求”这类需求的统一解法。

        事件循环：谁先谁后，一次说清

        JavaScript 只有一个主线程：同一时刻只能干一件事。 异步能成立，靠的是浏览器在背后排队，再用事件循环 （event loop）一条条取出来执行。队列有两条，优先级不一样：

        所以例 1 里 Promise.then 的回调会插在 setTimeout(…, 0) 前面：微任务永远比下一个宏任务先跑。 另外要记住：主线程被一段长循环占住时，定时器、点击回调、 页面渲染统统都得等——这就是“页面卡死”的真相。

        想知道 答案
        setTimeout(fn, 0) 会立刻执行吗？不会，它排在宏任务队列里，等当前同步代码和微任务都清完
        .then 和 setTimeout(fn, 0) 谁先？.then（微任务先于下一个宏任务）
        定时器时间是精确的吗？不精确，只是“至少等这么久”；主线程忙就顺延
        为什么长循环会让页面卡住？主线程只有一条，它没空，渲染和事件回调都轮不上

        本式小结

        • setTimeout 一次、setInterval 反复； 拿到编号就要想好什么条件下 clear，别让它一直跑；
        • Promise 三态：等待中 → 兑现或拒绝，只变一次； .then 接成功、.catch 接失败、.finally 收尾；
        • 组合多个任务：all（全成才成）、allSettled（全有结局）、 race（第一个有结局）、any（第一个成功）；
        • async 函数返回 Promise，await 等结果， 错误用 try/catch 接——异步的错误不会自己冒到你面前；
        • 事件循环：同步 → 清空微任务 → 一个宏任务 → 再清空微任务…… Promise.then 永远排在 setTimeout 前面；
        • 别用长循环霸占主线程；需要等的时候，就让代码“先记下、回头再说”。
        练功 · 第三十九式
        1. 做一个“三秒后提示”：点按钮，3 秒后页面上出现一行字； 再加一个「算了」按钮，能在时间到之前取消它 （提示：setTimeout 的编号存进变量）。
        2. 写一个 delay(ms)：返回一个 Promise，等 ms 毫秒后兑现 "等了 ms 毫秒"；再用 async/await + Promise.all 让三个任务（200 / 500 / 300 毫秒）并行， 最后打印总耗时。
        3. 思考：为什么 setTimeout(fn, 0) 的回调会排在 Promise.resolve().then(fn) 后面？如果主线程里有一段跑十秒的死循环， 这十秒里定时器回调、按钮点击、页面重绘会怎样？
        参考答案 1

        三个习惯：①编号存进变量，才有东西可取消； ②回调里把变量清回 null，下次才好判断“有没有在等”； ③先判断再开新的，避免连点攒出一堆定时器。

        参考答案 2

        总耗时约 500 毫秒而不是 1000 ——因为 Promise.all 里的三个任务 同时开工，等的只是最慢的那个。 顺手记住 delay 这个写法：以后想把 async 函数“暂停一下”就用它。

        参考答案 3

        因为两类回调排在不同的队列里：Promise.then 属于微任务， setTimeout 属于宏任务。 事件循环的规矩是“一轮宏任务结束后，先把微任务队列全部清空，再去取下一个宏任务”， 所以哪怕定时器写的是 0 毫秒，也得排在微任务后面。 至于十秒死循环：这十秒里主线程被占死，定时器回调不会执行、 点击事件不会派发、页面也不会重绘——浏览器把这几件事全推后了， 读者看到的就是“页面卡住了”。所以长任务要拆成小段， 或干脆交给异步流程排队去做。
