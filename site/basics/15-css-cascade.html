CSS 名字里的那个 C（Cascading）常被忽略，但它才是这门手艺的核心： 当多条规则同时指向一个元素，到底听谁的。 这一式把“谁说了算”的规矩一次讲清——它也是“为什么我这里改了没反应”的终极答案。

本式要点
  • 说清层叠的四步裁决：来源与重要性 → 层（@layer）→ 特异性 → 出现顺序
  • 知道哪些属性会继承、哪些不会，会用 inherit / initial / unset / revert
  • 知道 !important 什么时候值得用、什么时候是自找麻烦
  • 会按一份排查清单定位“样式不生效”的问题

层叠：四条裁决规则

浏览器给一个元素算样式时，会把所有命中的规则拿出来排队，依次比四件事—— 前面比出结果就不再看后面：

顺序 比什么 典型情况
1 来源与重要性 我们写的作者样式会盖过浏览器默认样式；带 !important 的比不带的更“重”
2 层（@layer） 同一来源内的普通声明：层里写的比层外写的弱；层与层之间按声明顺序，后声明的赢
3 特异性（权重） 第十四式的四位计分板：行内 > ID > 类/属性/伪类 > 元素/伪元素
4 出现顺序 四条全平：谁写在后面听谁的（“层叠”的字面意思）

把“来源与重要性”展开，会得到一张更细的顺序表（从弱到强，适用于普通项目的理解）：

  1. 浏览器默认样式（你能用 * { margin: 0 } 之类的重置盖掉它）；
  2. 用户自己设的样式（例如浏览器设置里“最小字号”——这是无障碍入口，别轻易无视）；
  3. 我们写的普通样式（日常写的都在这层）；
  4. 动画（@keyframes 正在播放时的值）；
  5. 我们写的 !important；
  6. 用户设的 !important；
  7. 浏览器默认的 !important；
  8. 过渡（transition 进行中的值，短暂但优先级最高）。

注意第 5、6 条：一旦加上 !important，来源的高低会反转—— 普通样式里作者赢过用户，带了 !important 之后用户反而赢过作者。 这不是设计失误，而是给读者留的一把“最终否决权”。

特异性与顺序的现场实验

第十四式讲了计分板，这里看它怎么实战。下面两条规则写的是同一个元素， 但一条用元素选择器、一条用 ID 选择器：

例 1 · ID 赢过元素；同分规则则后写者赢

我是普通段落：被元素选择器选中，所以是蓝色。

我带着 id="win"：ID 的分数更高，所以是朱砂色。

我带着 class="tie"：两条同分规则争我， 后写的那条（浅绿底）赢了。

你可以把演示里的两条 .tie 规则调换位置试试，背景色会跟着换—— 这正是“同分看顺序”。在真实项目里，样式表可能有几千行， 能靠“写清楚”解决的场合，就别靠“比谁写得靠后”。

继承：有些属性会“传给孩子”

第二个常被混淆的机制是继承：某些属性如果元素自己没有写， 就会取父元素的计算值。规律大致是——跟“文字”有关的会继承， 跟“盒子”有关的不继承：

属性 为什么
会继承 color、font-*、line-height、 letter-spacing、text-align、visibility、 cursor、list-style、direction 文字风格应该整段统一，不必给每个 span 重复写一遍
不继承 margin、padding、border、width / height、background、display、 position、overflow、box-shadow “盒子”的行为是每个元素自己的事，若继承会让布局灾难
例 2 · 文字样式会继承，盒子样式不会
我是父容器：设了颜色、字体、行高，还有一圈边框。 我是里面的 span：颜色、字体、行高都继承了，但我没有边框——盒子属性不外传。

有一个容易懵的特例：text-decoration（下划线、删除线）不继承， 但画的时候会“拖”到后代文字上——看上去像继承，其实不是。 你可以把它理解为“装饰沿着文本框画过去”，所以给父元素加下划线， 后代也会有下划线，但这跟继承机制无关。

四个关键字：inherit / initial / unset / revert

继承不是只能默默发生，也能手动指挥。每个属性都可以取这四个特殊值：

关键字 含义 例子
inherit 强行取父元素的值（对不继承的属性也管用） border: inherit 让子元素也长出一样的边框
initial 回到 CSS 规范里这个属性的初始值 color: initial 通常变回黑色（不是父元素色）
unset “没写”的意思：会继承的按继承处理，不继承的按 initial 处理 清掉一条本不该设的规则时最省事
revert 退回上一级来源（通常是浏览器默认样式） 在被打乱样式的页面里“回到原生样子”

还有一个大招：all 属性可以一次性作用于所有属性， 例如 all: unset 会把一个元素的所有样式清空（常用于隔离第三方组件）。

例 3 · 同一个父元素下，三个孩子三个说法

父元素：朱砂色、加粗、有边框。

子元素 color: inherit —— 还是朱砂色。

子元素 color: initial —— 回到默认的黑。

子元素 border: inherit —— 边框照抄父元素。

子元素 border: unset —— 边框消失（initial）。

!important 与 @layer：两个“打破常规”的工具

!important 写在声明末尾（分号之前），它让这条声明在 “来源与重要性”那一关直接升级。值得用的场合其实很有限：

  • 覆盖改不动的第三方样式（例如嵌入的组件库）时，作为最后手段；
  • 工具类（如“隐藏”“居中”这类单用途类名），需要稳定压过组件样式时；
  • 临时调试：确认一下某条属性到底能不能生效，查完就删。

它的代价也很明确：一旦用上，别人想覆盖你就只能也加 !important， 于是样式表里长出一串互相攀比的感叹号，谁也不知道最后听谁的。 能用选择器写清楚的地方，不要用感叹号。

@layer（分层）是较新的机制，它给样式表内部排了一个优先级序列： 层与层之间按“声明顺序”比较，后声明的赢；而层内写的普通规则， 整体比层外写的普通规则更弱。这带来一个非常好用的性质： 你可以把第三方样式或自己的基础样式放进层里，之后再写页面样式时， 不必堆选择器权重就能轻松覆盖。

例 4 · @layer：先声明的层反而输

这段文字来自 special 层（写在 base 层之前，却赢了）。

把 @layer base, special; 里的顺序对调，颜色就会翻转—— 这是“层与层之间按声明顺序，而不是按书写位置”的直接证据。 再仔细看一眼那圈边框：文字已经变成朱砂色，边框却还是灰的—— 因为那条 border 规则写在层外， 而层外的普通规则强过层内的普通规则，所以两个层里的 border-color 都没能改掉它。这正是分层机制的用法： 想让一部分样式“好被覆盖”，把它放进层里；想让它“稳如泰山”，就留在层外。

排查清单：样式为什么没生效

遇到“我改了没反应”，按这个顺序过一遍，九成的问题能在前三步找到：

  1. 选择器命中了吗：类名拼写、大小写、层级关系（.a .b 与 .a > .b 不同）；
  2. 打开开发者工具看 Styles 面板：命中的规则里，被划掉的那行就是输掉的那条， 右边还会写着它是被哪条规则盖住的；
  3. 是不是继承来的：你在容器上改颜色，孩子自己有规则就会不听话；
  4. 属性名或值写错：colour、font-size: 14（缺单位）、 全角冒号——这三样新手天天中；
  5. 样式表的顺序：后引入的样式表赢；
  6. 有行内样式或 !important 在场：它们的“分量”在前面几关就赢了；
  7. 缓存：改了文件却不刷新，先按一下 Ctrl + F5 强制刷新。

本式小结

  • 层叠四步：来源与重要性 → 层 → 特异性 → 出现顺序；前面分出胜负就不看后面；
  • 普通样式里作者 > 用户 > 浏览器默认；带 !important 时顺序反转；
  • 会继承的多是文字类属性，不会继承的多是盒子类属性；text-decoration 会“画过去”但不是继承；
  • inherit 取父值、initial 取规范初始值、unset 看属性是否默认继承、revert 退回上一层来源；
  • !important 只留给“覆盖第三方 / 工具类 / 临时调试”，它不是常规武器；
  • @layer 让顺序可声明、让基础样式好被覆盖；层外普通规则强于层内普通规则；
  • 样式不生效时，先看选择器、再看 DevTools 的划掉行、再看继承与顺序。
练功 · 第十五式
  1. 写三条指向同一段落的规则（元素、类、ID 各一条），预测谁赢， 再用开发者工具验证你的预测。
  2. 用 inherit 与 initial 各写一条规则， 让一个子元素分别“照抄父元素颜色”与“回到默认颜色”。
  3. 思考：为什么规范要让“用户的 !important”强过“作者的 !important”？ 它保护的是谁？
