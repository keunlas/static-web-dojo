上一式学会了改页面，可 page 凭什么知道该在什么时候动手？ 靠事件：用户的每一次点击、每一行输入、页面的每一次加载， 都是浏览器递过来的一声“到你了”。这一式就把“听得见动作、记得住谁点的”这件事讲透。

本式要点
  • 会用 addEventListener 绑事件、用 removeEventListener 解绑， 知道“同一函数不会重复绑”
  • 会读事件对象：type / target / currentTarget / key / clientX / preventDefault()
  • 讲得清冒泡与捕获，会看 eventPhase，会用 stopPropagation 与 once / capture 选项
  • 会把事件绑在父元素上做委托，并知道它为什么能照顾后来新增的元素
  • 会写防抖与节流，知道它们各自适合什么场景

事件驱动的思路

到目前为止，我们写的脚本大多是“页面一加载就把活干完”。真实的页面不是这样： 它大部分时间在等——等用户点、等用户敲、等数据回来。 所谓事件驱动，就是换一种写法：

这三行值得反复看，因为它是之后所有交互的地基：“什么时候做”交给浏览器， “做什么”由你写在回调里。回调这种“先写好、以后被叫”的函数， 第三十一式已经打过照面（如 setTimeout 的第一个参数就是回调）； 事件监听是它最重要的用武之地。

事件本身也是一个对象，带着“细节”一起送到回调里。下面是这个对象常用的成员：

成员 是什么 常见用途
type事件类型名（如 "click"）同一个函数挂多种事件时区分
target真正被点的那个元素（事件源头）委托时认“点到了谁”
currentTarget当前正在执行监听函数的元素回调里永远指向“绑事件的那个元素”
clientX / clientY鼠标在视口里的坐标（像素）跟随光标、拖动
key / code按下的键的“字符名” / “物理位置名”回车提交、Esc 关闭
timeStamp事件发生的时间戳（毫秒）节流、性能测量
eventPhase当前所处阶段（捕获 1 / 目标 2 / 冒泡 3）理解事件流、排查“为什么它也响了”
preventDefault()取消浏览器的默认动作拦表单提交、拦链接跳转
stopPropagation()阻止事件继续向外传播内层已经处理完，不想惊动外层

先别急着记全。先把点击、输入、键盘这三类事件用熟，其余用到时回来查即可。

this、currentTarget 与箭头函数的坑（第三十一式的回访）

用普通函数写监听器时，浏览器会把 this 设成当前元素，所以 this.value 能用；但箭头函数没有自己的 this， 它会顺着外层作用域往外找——在监听器里经常就找成了 window。 要稳，一律用 event.currentTarget 或提前存好变量， 别在箭头函数里依赖 this。例 2 会把这件事现场演一遍。

绑事件与解绑事件

把监听器挂上去的标准做法是 addEventListener(类型, 回调, 选项)。 第三种参数是选项对象，两个最常用的：

有些场景要主动解绑，用 removeEventListener(类型, 回调)。 它有一条容易被忽略的规矩：要解绑的函数，必须是当初绑上去的同一个函数。 所以监听器要解绑就先存进变量；写成匿名的字面量函数就没法再摘下来了。

另外，历史上有两种“老写法的马甲”： element.onclick = fn 和 HTML 里的 onclick="..." 属性。 它们的毛病是只能挂一个——后写的会把先写的顶掉。 本教程统一用 addEventListener，只在需要“整个替换掉原来的处理”时才会考虑 onclick（旧代码里则处处能看到它，读得懂就行）。

      input 与 change 的差别值得单独记一笔：前者“每敲一个字都响”， 后者“改完、离开才算”。同一个输入框，两种事件会给出完全不同的节奏—— 例 6 的防抖节流正好建立在这个差别上。

      事件流：冒泡、捕获与事件委托

      一次点击并不是只“发生在按钮上”。看图（这张图不是可运行的演示，是一张路线图）：

      事件从最外层一路捕获下来，抵达目标（真正被点的那个元素）， 再从目标一路冒泡回最外层；一路上的每个元素，只要挂了监听器都会被依次调用。 默认挂上去的监听器在冒泡阶段执行，所以“点按钮，卡片也听见了”—— 这不是 bug，是设计。每个监听器收到的 event.eventPhase 会如实告诉它此刻在哪一段。

      这条设计带来一个极其有用的技巧：把监听器挂在外层，让所有内层元素的事件冒泡上来处理， 这叫事件委托（event delegation）。好处有两个： 内层元素是几十个还是几万个，都只挂一个监听器；后来才新增的元素也不用再单独绑。

        stopPropagation() 是“这件事别再往外传了”，它不阻止同层其他监听器； 想让同一元素上后面的监听器也别跑，用更狠的 event.stopImmediatePropagation()（日常少用，用错会很难查）。 还有一个常被混淆的家伙：stopPropagation 管“传播”， preventDefault 管“浏览器默认动作”，两者互不相干—— 下一节就见它出场。

        默认行为与取消

        浏览器给很多元素配了“不用写 JS 就有的动作”：点链接就跳走、提交表单就刷新页面、 输入框里按键就出现字符……这些叫默认行为。 当你想自己接管时，就在事件回调里调用 event.preventDefault()。

            委托的三个注意点
            • 必须会冒泡的事件才能委托。focus / blur / mouseenter / mouseleave 不冒泡，委托它们要用各自的 focusin / focusout / mouseover / mouseout；
            • 认“点的到底是谁”，别直接拿 event.target 当条目： 按钮里可能还套着图标或 <span>，标准做法是 event.target.closest(选择器)；
            • 回调开头先守卫：拿不到目标就 return， 免得点列表空白处也被当成一次“删除”。

            高频事件：防抖与节流

            有些事件触发得太勤了：input 每敲一个字一次、scroll 和 mousemove 每秒能来上百次。如果回调里要做正经事（搜接口、算布局、存数据）， 就得给它降速。两种最常用的策略：

            • 防抖（debounce）：先等一等，如果等待期间又响了，就重新计时； 事件停下来之后只跑一次。适合“输入完再搜”“窗口调完再重排”。
            • 节流（throttle）：不管响多少次，每段固定时间内最多跑一次。 适合“滚动时更新进度”“拖动时跟手”。

            两个函数都返回一个新函数——这正是第三十一式的闭包： timer 与 last 被关在各自的小盒子里， 外部看不见，却能在每次调用之间“记得住上次”。这也是为什么闭包必须学扎实： 它不只是面试题，是这类工具的骨架。

            原样响应0 次每一下都跑（多热闹也多费劲）
            防抖（停手后再跑）0 次连敲 5 个字，只跑 1 次
            节流（400ms 最多一次）0 次连点 5 次，只跑 1 次

              怎么读这张表：连敲几个字，原样一栏会跟着字数往上跳，防抖一栏 要等你停手约 400 毫秒才 +1，节流一栏在连续输入里隔一段加一次。 这也是为什么“实时搜索”要防抖（只在停手后请求一次）， “滚动进度条”要节流（跟随手感，又不至于每像素都算）。

              撤销与清理：别让监听器变成漏水的龙头

              元素被删掉时，它身上的监听器通常也会被垃圾回收带走，一般不用手动清； 但长期存在的对象（window、document、定时器、 以及你自己写的发布订阅）如果绑了监听器又不解，就会一直占着内存、甚至重复触发。 规矩：给“临时出现的界面”绑的监听器，界面消失时记得解绑， 或者在绑定时就用 { once: true } 说清“只管一次”。

              本式小结

              • 事件驱动＝“先写好回调，等浏览器来叫”；绑定用 addEventListener(类型, 回调, 选项)，解绑必须传同一个函数；
              • 事件对象先记 target 与 currentTarget：前者是“被点的”， 后者是“正在听的”；key 读按键、clientX/Y 读坐标；
              • 事件流是“捕获 → 目标 → 冒泡”，默认监听器在冒泡阶段跑； { capture: true } 改到捕获阶段，eventPhase 能看出在哪一段；
              • 事件委托＝把监听器挂在父元素上，用 event.target.closest(选择器) 找目标；动态元素因此不用重新绑；
              • preventDefault() 拦默认动作（表单提交要拦 submit）， stopPropagation() 断传播，两件事互不相干；
              • 高频事件用防抖（停手后跑一次）或节流（每段时间最多一次）， 两者都靠闭包记住上次的时间或定时器。
              练功 · 第三十八式
              1. 做一个“待办清单”：输入框回车或点按钮都能新增（提示：表单的 submit 事件自带回车提交），列表用事件委托处理删除与勾选完成。
              2. 给搜索框加防抖：停手 300 毫秒后才在结果区显示“正在搜索：某某”—— 要求自己写那个 debounce，别复制例 6 的。
              3. 思考：为什么 stopPropagation() 不能让例 3 里的 捕获阶段监听器不执行？如果你真的想让外层在捕获阶段也收不到， 该怎么办？
              参考答案 1

              三个细节：①用 <form> 白拿回车提交与 required 校验； ②勾选用 change（勾选/取消都会响），删除用 click， 两个事件各管一摊、都靠委托；③回调开头用 closest 判断“这是不是我要管的”， 不是就直接返回。

              参考答案 2

              注意箭头函数版本的 fn.apply(this, args)：箭头函数自己没有 this，这里的 this 取自外层——如果包装的是普通函数、又需要 this 指向元素，就用普通函数写包装器（像例 6 那样）。

              参考答案 3

              因为捕获阶段比冒泡更早发生：事件从 document 往下走， 先经过外层元素的捕获监听器，才会抵达目标；等目标上的监听器调用 stopPropagation() 时，外层的捕获监听器早就执行完了。 这也说明了一件事：“阻止传播”只对还没走到的后续阶段有效。 真想让外层的捕获监听器也别响，得在更外层（更早的阶段）就拦住， 或者在 document 的捕获阶段统一处理。 这正是“先看清楚谁早谁晚，再决定在哪里拦”的实际意义。
