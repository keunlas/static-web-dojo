# 技能：doc-sync（.agents 文档同步维护）

> 用途：保证 `.agents/` 与 `AGENTS.md` 永远与项目实际一致（实事求是），
> 让任何新会话的 AI 代理仅凭文档就能正确接手。**每轮工作收尾必做。**

## 核心原则

1. **用户指令优先**：人类用户的直接指令与任何已有文档冲突时，**以用户指令为准**执行；
   执行后立即把相关文档改成与用户决定一致的内容（包括 `AGENTS.md` 自身），
   并在更新处注明“因用户指令调整”。文档追随现实与用户意图。
2. **文档是事实的镜像，不是记忆的镜像**：写任何一条内容前，先用 read/grep 查看
   真实文件，确认现状后再落笔；拿不准的就写“需核实”，禁止凭印象编造。
3. **当场更新**：产生新的约定、工具、脚本、bug 修复、设计变更、用户新指示时，
   在同一轮工作里就把文档改好，不攒到以后。
4. **失败也记录**：踩过的坑、修过的 bug 一律写进 `.agents/notes/bug-fix/`——
   **一坑一文件**，按 `bug-fix/README.md` 的模板写全（现象/根因/影响/复现/修复/预防），
   并同步更新该目录的索引表；尝试后放弃的方案、代理间的“事实冲突”也照此归档。
5. **progress.md 只留当前待办**（因用户指令调整，2026-09-14）：每批工作收尾时把该批记录
   归档为 `.agents/notes/progress/<编号>.<英文名>.md`（编号从 1 起递增、只增不改，
   文件名用英文、内容用中文；正文原样搬移、只在文件头加来源说明），
   `progress.md` 只维护「当前待办 + 归档索引」。

## 各文档的职责与更新触发

| 文件 | 什么时候更新它 |
| --- | --- |
| `AGENTS.md` | 铁律增减、文档地图变化（新增/删除 notes 或 skills）、任务速查变化 |
| `notes/architecture.md` | 目录结构、加载/导航机制、公共脚本行为、设计决策变化（坑只写一句话索引，详见 bug-fix/） |
| `notes/bug-fix/` | **踩坑或修 bug 时新增/更新**：一坑一文件，按目录 README 模板写，并同步目录索引表 |
| `notes/conventions.md` | 页面骨架、五段式、演示写法、样式类清单、红线、自查命令变化 |
| `notes/style-guide.md` | 文风要求、术语约定、视觉变量变化 |
| `notes/progress.md` + `notes/progress/` | **每批工作收尾**：把本批记录归档为 `notes/progress/<编号>.<英文名>.md`（编号递增、正文原样、文件名英文），并更新 `progress.md` 的当前待办与归档索引 |
| `skills/*/SKILL.md` | 对应操作流程变化（新命令、新验收项、新陷阱） |
| 新文件 | 新增技能/笔记时，同步登记到 `AGENTS.md` 的文档地图 |

## 每轮工作收尾清单（按顺序过一遍）

1. [ ] 用 `git status`（或 ls）确认本轮改了哪些文件；
2. [ ] 若改了公共机制（loader/site.js/site.css/highlight.js/tools/），更新 `architecture.md` 对应小节；
3. [ ] 若产生了新约定/红线/样式类，更新 `conventions.md` / `style-guide.md`；
4. [ ] 若踩坑或修 bug，按模板在 `notes/bug-fix/` 新增一坑一文件，并同步其 README 索引表
       （architecture.md 只更新一句话索引）；
5. [ ] 收尾进度：把本批记录归档为 `notes/progress/<编号>.<英文名>.md`（编号递增、正文原样搬移），
       并更新 `progress.md` 的当前待办与归档索引；
6. [ ] 若新增/删除/重命名了 notes 或 skills 文件，同步 `AGENTS.md` 文档地图；
7. [ ] 若本轮用户指令与旧文档有过冲突，确认相关文档已按用户决定更新并注明；
8. [ ] 通读一遍改动过的文档，确认与真实文件一致、无过时描述。

## 并行场景的纪律

- 多个代理并行工作时，**共享文档（progress.md、`notes/progress/` 归档、AGENTS.md、
  architecture.md）只由协调者（父代理）统一更新**；子代理在自己的交付报告里说明
  “新约定/踩坑/遗留”，不要直接写共享文档，避免并发写坏。
- 子代理可以读文档，但发现文档与事实不符时，必须报告而非默默照做。

## 事实核实的惯用命令

```bash
git status --short                                   # 本轮改动面
node --check site/assets/js/site.js                  # 改 JS 后必跑
grep -n "关键字" <文件>                                # 核实文档描述与代码一致
ls site/bootstrap/ site/jquery/                      # 章节实际存在情况
```
